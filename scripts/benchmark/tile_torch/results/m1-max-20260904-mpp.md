# Hand-written MPP closes most of the measured MPS gap

On this M1 Max, a hand-written, full-FP32 MPP kernel reaches roughly MPS
performance on 1024³ and 2048³ GEMM and is faster on the tested small/ragged
cases. Two long-K rectangular cases still trail by about 7–9% in paired GPU
batch time. **This is not a TileIR-to-MPP lowering result:** the production
planner cannot emit these plans yet.

## Evidence and protocol

- [Six-order frozen replay](m1-max-20260904-mpp-replay/results.md),
  [raw replay](m1-max-20260904-mpp-replay/results.json).
- [Six-candidate, eleven-shape screen](m1-max-20260904-mpp-search/results.md),
  [raw screen](m1-max-20260904-mpp-search/results.json).
- [Additional rectangular search](m1-max-20260904-mpp-rect-search/results.md),
  [raw search](m1-max-20260904-mpp-rect-search/results.json); exploratory only.

The principal screen has 77 validated outputs. Its frozen replay has 198
validated outputs: eleven shapes, six rounds, three implementations (MPS,
default MPP, selected MPP). Every complete output is compared with an FP64
oracle, `atol=rtol=1e-4`. No failed or slow round is dropped. All tests use
compact row-major FP32 A/B/C, alpha=1, beta=0, no prepacking, no reduced-precision
permission, and no compiler fast math in MPP. Inputs follow the existing
deterministic benchmark pattern; this is not a comprehensive floating-point
accuracy suite. Output starts as NaNs to check independence from previous C.

Each process warms up for 200 ms and measures nine approximately 40 ms batches
in replay. Shape order rotates and each shape visits all six implementation
orders. Compilation, allocation, upload and validation are outside timing.
No builds or other agent-run GPU tests overlap the performance campaigns.
The operating system/display and user activity are not under exclusive control.

MPP uses `tensor_inline` over private buffers and the classic tracked command
queue, as does the direct MPS baseline. Both record host wall times and Metal
command-buffer GPU intervals. GPU intervals still include batch dispatch and
synchronization; small-kernel gains are not pure arithmetic throughput claims.
The optional Metal 4 tensor-handle path is not used in the main comparison.

Ratios are paired medians, not ratios inferred from unrelated historic runs.

| 513×257×129 | 34.024 | 27.184 | 24.298 | 0.714 |

For 1024³ the paired range is `[0.917, 1.000]`; for 2048³ it is
`[0.934, 1.040]`. Treat both as approximately MPS-level, not a universal or
statistically established speedup. The long-K rectangles are slower in every
principal replay round. The additional rectangle-only screen encounters a
different timing scale and visible within-run drift; it does not overturn this
result or authorize a new default plan.

## The useful execution distinction

Default MPP means one `64×64` operation cooperating across all four subgroups
of a 128-thread group. It is not the fastest tested organization.

All selected candidates use one-subgroup operations with cooperative output,
dynamic K and inline tensor views:

| Shape(s) | Per-operation tile | Subgroups per group | Cohort rows×columns |
|---|---|---:|---|
| 32³, 128³, 1024×128×256, both ragged cases | 16×16 | 1 | 1×1 |
| 512³, 256×2048×1024 | 32×32 | 8 | 8×1 |
| 1024³ | 32×32 | 4 | 4×1 |
| 256×1024×128 | 32×32 | 4 | 2×2 |
| 2048³, 2048×256×1024 | 32×32 | 1 | 1×1 |

For 1024³, the group produces a `128×32` rectangle through four independent
`32×32` subgroup operations. The execution map composes with separate A/B/C
views. No explicit shared-memory staging appears in the hand-written kernel;
MPP owns any internal staging and fragment arrangement. We have not measured
its internal register allocation or claimed that it never uses shared memory.

The `16×16` candidate helps small and ragged cases but is much worse on large
square GEMM. This is direct evidence against replacing one fixed schedule with
another fixed schedule. Operation scope, outer cohort geometry, active group
count, tails and K extent must survive in the candidate/model fingerprint.

The [planner integration contract](../../../../docs/source/internals/tile/planner.md#native-mpp-experiment-operation-scope-is-not-launch-size)
keeps legality separate from ranking. The immediate next implementation work
is typed operand-view forwarding with snapshot/alias checks, an MPP-capable
Metal emitter, and a candidate family that can express both whole-group and
independent-subgroup execution. Until then the samples are an empirical target
and solver experiment, not coefficients for the existing native-8×8 model.

## Reproduction and artifact identity

Use [`compare_mpp.py`](../compare_mpp.py) and the commands in the
[benchmark README](../README.md#native-mpp-versus-mps). Rebuilding changes the
executable hash; run a fresh search before replay rather than bypassing the
frozen-artifact check. The committed report records base revision `6f6711d35`
and a dirty worktree. These standalone binaries do not link TileIR or TVM, so
the unrelated in-progress late-prefetch and barrier edits cannot affect them.

After freezing the measured MPP artifact, the source gained an old-SDK
diagnostic guard and a host compiler-version JSON field. Neither changes the
shader, bindings or timed dispatch path. The rebuilt source is checked again
for compilation and complete-output correctness; the table above remains the
unaltered frozen-artifact replay, not a measurement of the rebuilt binary.

Validation of the final source: full `cmake-build-tirx` build; Objective-C++
syntax checks for both probes; 32 benchmark-driver unit tests; direct system
CPU/Metal self-tests; and 20 additional full-output checks covering tiny,
ragged and aligned cases, inactive cohort members, direct/cooperative output,
and the Metal 4 handle path. These short smoke timings are not added to the
performance table. Older-SDK diagnostic compilation was not tested with an
actual older Xcode installation.
