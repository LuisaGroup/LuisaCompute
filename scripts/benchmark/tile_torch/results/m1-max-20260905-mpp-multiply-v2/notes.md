# TIRx Metal MPP contract v2: zero-fill removed, Torch gap closed

This report records the first structural TIRx→Metal MPP optimization whose
benefit survives the full seven-path replay. It is not a claim that Tile has
universally matched vendor libraries: CPU GEMM remains structurally behind,
1024³ is still marginally behind direct MPS under the previously frozen plan,
and production-size non-GEMM LLM operators have not yet been timed here.

## Result

All **784/784** complete outputs passed the same FP64 oracle. The run covers
eight square, rectangular and ragged FP32 GEMMs, seven independent paths,
fourteen position-balanced rounds, seven samples per row, 30 ms sample targets
and 200 ms warmup. No failed or slow row was discarded. Every benchmark binary
and externally linked TVM compiler/runtime artifact retained its before/after
SHA-256. [Raw samples and provenance](results.json) and the
[complete generated table](results.md) are retained beside this report.

The displayed times are medians of within-round p50s. Ratios are medians of
same-round ratios, not ratios of the displayed medians. They are synchronized,

encoding/submission and synchronization. They are not GPU-event durations.

The frozen v2 TIRx MPP-view plan is faster than Torch on all eight shapes and
faster than MPS on seven. At 1024³ it is 3.8% faster than Torch, 4.7% faster
than native Tile→MPP, 12.3% faster than ordinary TIRx, 0.4% slower than MPS and
2.9% slower than handwritten MPP by paired ratios. The earlier v1 balanced run
measured 291.736 µs for this path; v2 measures 273.996 µs, a descriptive 6.1%
reduction across the two independent replay sessions.

## Structural defect and repair

The Tile program initializes its accumulator with `zeros`, then performs one
full-K `mma`. Before v2, lowering materialized a cooperative destination,
unrolled a per-fragment loop that wrote zero into every valid element, selected
MPP `mode::multiply_accumulate`, and finally called `.run(A, B, D)`. The
handwritten MPP control instead used the default overwriting multiply mode and
never initialized D.

Contract v2 adds a typed
`tirx.cooperative_tensor_multiply_from_memory(D,A,B,M,N,K,layouts)` operation
with semantics `D=A*B`. The existing operation remains `D=A*B+C`. Metal
codegen records the operation mode on the cooperative-tensor allocation,
rejects mixed/inconsistent modes, selects the corresponding typed MPP
descriptor, and never infers semantics from names or emitted text.

The bridge selects overwriting multiply only when all of these are proved:

1. the canonical MMA matcher accepted FP32 arithmetic with explicit
   reassociation permission;
2. the initializer is a literal **positive** zero;
3. for a pipeline carry, allocation, initialization, recurrence and direct
   output form a closed use region with no observation or escape;
4. the recurrence has exactly one static iteration; and
5. the existing ownership, bounds, full-subgroup participation and MPP shape
   checks still pass.

Nonzero C, negative zero, memory C, two or more K iterations, observed/escaped
carry state, unsupported layouts and unproved direct outputs keep the original
multiply-accumulate path. This is why the optimization affects the frozen
full-K 32³, 128³ and 1024³ schedules, while the five multi-step/ragged schedules
remain accumulation controls.

The content-addressed [1024³ Metal source](sources/a40bb96e137812580781e37554dded7d868cdf702e3d606b88d4a43528408cf7.metal)
contains one `mode::multiply`, one `.run()`, no `get_capacity()` zero-fill loop,
zero shared-memory bytes and the two conservative subgroup-boundary barriers
reported by the planner. The source is generated by TVMx's native C++ Metal
codegen; it is not rewritten text and does not call Luisa's native MPP emitter.

## What remains in the planner

The frozen 1024³ schedule predates v2 and uses a 64×64×1024 outer tile, 128
threads and a 2×2 subgroup grid. Its `GroupPlan::cost` is still explicitly
tagged `simdgroup_reference_geometry`; fields such as matrix issues, fragment
transfers and per-lane scalars do not model MPP's internal implementation.

A separate, correctness-checked 128×32×1024, 128-thread, 4×1 probe produced a
byte-identical output and measured a 270.66 µs median with the same conservative
barriers. The same geometry with independently proved fence elision measured
264.50 µs. These are unbalanced exploratory measurements, not replacements for
the table. They nevertheless show that the remaining 1024³ gap is schedule
ranking: even without fence elision, a legal alternative is below the replay's
272.694 µs MPS median.

The next cost model must distinguish at least realization family, pure versus
accumulating MPP mode, local rectangle aspect ratio, subgroup cohort, K
granularity, global-view versus staged operands, edge policy, barrier protocol
and dispatch overhead. Exact enumeration is still adequate for today's small
candidate set. Calibration and held-out regret should precede adding ILP,
annealing or a larger learned solver; the 128×32 observation must not become a
hard-coded 1024³ rule.

## Correctness and build gates

The patched TVM tree and Luisa tree both completed full builds. Project syntax
checks report no diagnostics for every changed Luisa C++ file. Targeted gates
pass:

- `test_tile_tirx_matrix_metal`: real Metal source and execution, including the
  new pure mode, nonzero/literal C, multi-iteration fallback, transposes,
  ragged tiles, aliases, escapes, manual Memory and malformed contracts;
- `test_tile_tirx_matrix`: CPU/reference matrix regressions; and
- `test_tile_native_runtime`: Luisa Runtime offsets, guards, aliases and shader
  ownership.

The pure-mode regression also asserts that a one-step positive-zero recurrence
contains `mode::multiply` and no fill loop, while an otherwise identical
two-step recurrence contains `mode::multiply_accumulate` and the initialization.
Both execute twice with changed non-dyadic inputs. The 1024³ exploratory output
is byte-identical to the prior MPP result and CPU reference (SHA-256
`dc874b267d68843823c6d03645561fec905db7974ec0f61242330fdddb927e78`).

After final clang-format of the TVM extension, TVM rebuilt all 427 scheduled
objects and relinked successfully; the selected Luisa tree then completed its
full rebuild against those dylibs. The final 25-test CPU/Metal Tile cohort is
23/25 passing. Its only failures are the separately documented, pre-existing
`test_tile_tirx_cooperative_metal` and `test_tile_tirx_memory_metal` assertions:
the tests expect `mem_flags(3)` while an unowned worktree edit emits
`mem_flags(2)`. No assertion or unrelated edit was changed. The three direct
gates above pass after the final relink, and the Python benchmark-contract
suite passes 60/60.

A short post-build 1024³ probe used the frozen 64×64×1024 plan, 128 threads,
one pipeline window and the conservative two-barrier policy. It is not another
balanced performance result. Its generated source is byte-identical to the
archived source above (SHA-256
`a40bb96e137812580781e37554dded7d868cdf702e3d606b88d4a43528408cf7`),
contains exactly one `mode::multiply` and one `.run()`, and contains neither
`mode::multiply_accumulate` nor `get_capacity()`. Its output again has SHA-256
`dc874b267d68843823c6d03645561fec905db7974ec0f61242330fdddb927e78`.

TVM is pinned to `c7b458e946bc4266915da582457476bdcd9705ae`; tvm-ffi is

## Reproduction

After applying the v2 patch and completing both full builds and correctness
tests, run:

```sh
uv run --no-project --python 3.13 --with torch --with numpy python \
  scripts/benchmark/tile_torch/compare_lowerings.py \
  --native /tmp/luisa-tvm-mpp.VaKmzx/luisa-build/bin/benchmark_tile_native \
  --tirx /tmp/luisa-tvm-mpp.VaKmzx/luisa-build/bin/benchmark_tile_tirx \
  --mpp /tmp/luisa-tvm-mpp.VaKmzx/luisa-build/bin/benchmark_tile_mpp \
  --mps /tmp/luisa-tvm-mpp.VaKmzx/luisa-build/bin/benchmark_tile_system \
  --mpp-plan scripts/benchmark/tile_torch/results/m1-max-20260904-mpp-search/results.json \
  --tirx-plan scripts/benchmark/tile_torch/results/m1-max-20260904-joint-search/results.json \
  --tirx-mpp \
  --tirx-view-plan scripts/benchmark/tile_torch/results/m1-max-20260904-tirx-views-plan.json \
  --compiler-artifact /tmp/luisa-tvm-mpp.VaKmzx/build/lib/libtvm_compiler.dylib \
  --compiler-artifact /tmp/luisa-tvm-mpp.VaKmzx/build/lib/libtvm_runtime.dylib \
  --compiler-artifact /tmp/luisa-tvm-mpp.VaKmzx/build/lib/libtvm_runtime_metal.dylib \
  --compiler-artifact /tmp/luisa-tvm-mpp.VaKmzx/build/lib/libtvm_ffi.dylib \
  --rounds 14 --samples 7 --sample-ms 30 --warmup-ms 200 \
  --output /tmp/tile-mpp-v2-replay
```

Native/handwritten MPP use fast math off and relaxed precision off. TVMx's
current Metal runtime hardcodes fast math on. That policy difference is
recorded, not hidden, and prevents calling this a strict same-codegen GPU A/B.
