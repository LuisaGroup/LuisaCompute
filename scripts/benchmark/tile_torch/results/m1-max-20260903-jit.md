# M1 Max：Staged/JIT、重复测量与 profiling

这轮确认了两类不同的收益：普通 C++ 参数重新 capture/JIT 的分块搜索，
以及 profiling 后删除冗余 yield 快照的通用 lowering 优化。它们分开做 A/B，
不把调参收益算成编译器 pass 的收益，也不把不同时间段的加速比相乘。

同时确认了边界：CPU 自动 SIMD packing 仍不宜默认开启；更大的 Metal
分块也不是可靠的下一步。当前大 GEMM 仍落后于 PyTorch 使用的 Apple 库。

## 测量口径与完整性

- Apple M1 Max，macOS 26.6.2；PyTorch 2.14.0，构建提交
  `08187d9e0fba026dc8217405802ab5381dc88d90`；CPU 线程设置为 8。
- FP32，确定性的 dyadic 输入，完整输出对照 CPU FP64 oracle；不是随机抽样检查。
  GEMM 包含 8 个方形、长宽不等及非整除尺寸；CPU 另外覆盖 add、sum、softmax
  各 4 个尺寸。没有把这些结果推广为其他 dtype、stride 或任意输入的性能结论。
- 下列 11 份报告共有 **500 次最终/复测比较 + 192 次搜索比较 = 692 次
  native/PyTorch 比较**，全部通过数值验证。每次比较的两端各有 9 个吞吐和
  9 个延迟样本；重新审计了样本数量、有限正值和 p50。原始失败/慢结果不删除。
- 这些数据中 CPU native 最大绝对误差为 `3.5371e-9`，CPU PyTorch 为
  `2.6781e-9`；Metal 两端为 0。零误差依赖本次输入，不能推广为 FP32 MMA
  在所有输入上与 FP64 精确相等。
- 时间为预分配、驻留输入的 **warm、同步 host-wall time，包含 dispatch**，
  不是纯 GPU 时间。capture、JIT、首次调用、传输单列；搜索耗时也单列。
- 四轮复测冻结配置、轮换尺寸、交错 native/PyTorch 与候选顺序；每次 native
  都重新启动进程、capture/JIT 并检查完整输出。表中时间为各轮 p50 的中位数；
  加速比是每轮配对比值的中位数。min–max 是观察范围，**不是置信区间**。
- profiling 与构建不和性能复测同时运行。机器接 AC 电源；未记录到系统 thermal
  warning，但这不证明频率恒定。后面的搜索和 A/A 对照确有明显波动，不能横向
  拼接不同时段的绝对时间或把一次搜索的最小值当成稳定性能。

## 1. 普通 host 参数的多次 capture/JIT 有效

Metal 最初比较 `8×8×16 / window 2` 与逐尺寸选择的配置，四轮复测中 32 个
配对全部加速。以下是复测结果，不是搜索过程的最小耗时：

| GEMM M×N×K | 原配置 µs | 选中配置 µs | 配对加速中位数 [范围] |
|---|---:|---:|---:|
| 32³ | 5.289 | 4.214 | 1.289× [1.098, 1.401] |
| 128³ | 14.057 | 7.389 | 1.895× [1.714, 2.093] |
| 512³ | 348.420 | 125.049 | 2.787× [2.769, 2.795] |
| 1024³ | 2483.813 | 931.848 | 2.667× [2.660, 2.672] |
| 256×1024×128 | 87.082 | 36.836 | 2.357× [2.294, 2.422] |
| 1024×128×256 | 94.889 | 36.247 | 2.627× [2.597, 2.659] |
| 127×193×61 | 9.812 | 8.004 | 1.228× [1.077, 1.414] |
| 513×257×129 | 63.612 | 35.773 | 1.766× [1.749, 1.859] |

见 [固定配置四轮报告](m1-max-20260903-repeat-metal/results.md)。
64 个 Metal 搜索候选总 selection wall time 为 55.417 秒，包含验证及框架计时，
不是纯编译时间。最终配置多数为 `16×32×32` 或 `16×32×64`，window 按形状选择。
不需要 capture-once 超级图，也未增加 DSL 层的调参实体。

CPU 的 48 个候选搜索和 20 case 的四轮 SIMD packing 比较没有给出统一结论。
例如 `add 1×127` 配对加速 1.593×，`add 4096×256` 为 1.212×；但
`GEMM 513×257×129` 为 0.870×，四轮均回退；`softmax 1×127` 也均略慢。
因此 `auto_vectorize` 保持 opt-in，而显式 vector scope 不受影响。
见 [CPU packing 四轮完整报告](m1-max-20260903-repeat-cpu-vector/results.md)。

## 2. 从真实 capture 得到的 lowering 优化

PyTorch CPU 实际进入 Accelerate BLAS；默认 MPS GEMM 实际进入
`NDArrayMatrixMultiplyNNA14`。1024³ 的 MPS capture 是 512 个 threadgroup、
每组 128 线程、12 KiB 动态 threadgroup memory。Xcode 单次 replay 的占用率
18.39%，ALU 利用率却有 76.83%。详细来源、计数器、适用条件及不可推断项见
[profiling 记录](m1-max-20260903-profile.md)。

我们的旧 MSL 则把已物化的 MMA 结果再复制成 yield 快照，随后才更新 carry。
`2e0172700` 消除这类已稳定值的重复快照，仍先保存所有依赖旧 carry 的表达式，
再同时更新各 carry；没有放宽 alias 或算术语义，也没有为 GEMM 泄露 DSL 抽象。

对于 `16×32×32 / window 1`：shared 数组从 12 KiB 降到 10 KiB，
每个 K chunk 的源码 barrier 从 5 次变为 4 次，MMA 和 launch 不变。
下面使用保存的旧二进制/共享库与新二进制，在**完全相同的逐尺寸配置**下比较：

| GEMM M×N×K | 修改前 µs | 修改后 µs | 配对加速中位数 [范围] | 同轮 PyTorch µs |
|---|---:|---:|---:|---:|
| 32³ | 4.598 | 4.507 | 1.001× [0.973, 1.025] | 30.304 |
| 128³ | 8.077 | 7.684 | 1.053× [1.036, 1.077] | 30.721 |
| 512³ | 148.006 | 116.137 | 1.271× [1.227, 1.344] | 55.986 |
| 1024³ | 1095.253 | 980.069 | 1.120× [1.070, 1.159] | 339.288 |
| 256×1024×128 | 43.254 | 37.313 | 1.167× [1.125, 1.181] | 33.812 |
| 1024×128×256 | 42.072 | 33.530 | 1.256× [1.163, 1.321] | 35.126 |
| 127×193×61 | 8.600 | 8.766 | 0.995× [0.934, 1.014] | 31.210 |
| 513×257×129 | 40.937 | 38.459 | 1.072× [1.038, 1.102] | 40.442 |

小尺寸不能宣称普遍收益。512³/1024³ 仍分别约为 PyTorch 耗时的 2.07×/2.89×，
尚未达到库级性能。[CPU 同参数二进制 A/B](m1-max-20260903-repeat-cpu-yield/results.md)
的每个形状都同时出现加速/回退轮次，不能宣称可靠的 CPU 提速；1024³ 的配对
中位数为 1.010×，范围 [0.803, 1.187]。

## 3. 更大的块没有通过独立复测

增加 `32×32×32`、`32×64×32`、`64×32×32`，连同两个现有块和 window 1/2，
共验证了 80 个候选，selection wall time 为 73.680 秒。两个最大块没有赢得
任何形状；32³ 的一次搜索选中了 `32×32×32 / window 2`。

随后再用相同的新二进制，对旧计划和新计划做四轮冻结复测。32³ 的新计划四轮
均慢，配对加速仅 0.936×；宽矩阵的新计划为 1.033× [0.935, 1.382]，收益
并不可靠。其余六个形状的计划实际相同，是 A/A 对照，也可见噪声。因此不把
这次搜索结果升级为推荐计划。原始搜索及复测均保留，见
[搜索记录](m1-max-20260903-jit-metal-profile-guided/results.md) 和
[独立复测](m1-max-20260903-repeat-metal-profile-guided/results.md)。

下一步应集中于 target lowering 的 accumulator 复用/寄存器驻留、按依赖放置
barrier，以及 CPU worker-local scratch 规划。CPU LLVM IR 仍在逻辑 output-tile
循环中调用 workspace allocator。MPS 的 launch 数据不能替代这些资源/数据流设计，
也没有证据支持直接复制一个 `128 threads` 常数就能解决差距。

- 修改的 C++ 文件分别通过单文件语法检查和 clang-format。

  测试通过，包含 CPU/实际 Metal、多 carry、交换、零次迭代及 pipeline window 1/2。

- Python 驱动 **17/17** 单测通过；修正后的 Metal capture 目录实测产出
  `0000-gemm.gputrace`，32³ 结果正确；`git diff --check` 通过。
